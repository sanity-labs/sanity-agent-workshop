# Checkpoint 2-4 · Put a human in front of it

_Correct on any project — this mission doesn't depend on the seed._

**Files.** `studio/workflows/menu-item-review.ts` exports a `defineWorkflow` named
`menu-item-review` with stages `drafting`, `review`, `approved`; `studio/sanity.workflow.ts`
exports a `defineWorkflowConfig` with `tag: 'production'` and `workflowResource` id
`<yourProjectId>.production`. `sanity.config.ts` is unchanged. No schema changes.

**Deploy.** `--dry-run` printed a JSON diff of the definition. The real deploy printed:

```
✔ Processed 1 definition(s) · production (production) → <projectId>.production
  ✔ created   menu-item-review v1
```

**In the Studio.** Create a **new** menu item (a fresh document — `autoStart` doesn't apply to
existing ones). The workflow strip above the form shows **Drafting**, no Start button needed.
The **Workflows** tab beside the editor lists _Draft the description and allergen callout_; firing
_Submit for food-safety review_ moves the strip to **Food-safety review**. The item is now held:
_Approve_ is the only way forward in the UI. Firing it moves the strip to **Approved**.

**The history feed.** In the Workflows tool (navbar) → Overview → your run → the detail panel:
entries for the start, the submit action, the transition to review, the approve action, the
transition to approved — each with who and when.

**The honest demonstration.** Create another new item and publish it straight from the document
without touching the Workflows tab. The instance still advances — the transition reads the
document's state, not the button. That is the expected result, not a bug: the engine observes,
the Content Lake enforces, and lake-side guard enforcement hasn't shipped.

**If the Workflows tab is empty**, the deploy tag doesn't match the plugin's tag, or the
definition name isn't `menu-item-review`. **If the strip offers "Start workflow"** instead of
auto-starting, the document already existed.

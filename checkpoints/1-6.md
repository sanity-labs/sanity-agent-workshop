# Checkpoint 1-6 · Draw the boundary

_Correct if you're still on the Green & Gather seed._

**No code changed.** The only change is `groqFilter: status == "published"` on your MCP in the
Context app.

**Winter Miso Bowl attempts.** For every phrasing, the trace shows a `groq_query` and an **empty
result** — `resultCount: 0` — or a query that never matches the item. The agent says it can't
find such an item. It does **not** say "I know about it but can't discuss it" — it genuinely
cannot see the document. The `meta.executedQuery` may show your filter combined into the query
with `&&`.

**"How many vegan options do you have?"** **7**, even if the agent's own query omits `status`.
Before the filter, that omission gave 8.

**The KB probe** (if the route has the knowledge base from 1-3). `read_food_safety_kb` or
`knowledge_base_read` finds no entry for the bowl; the agent may fall back to GROQ, which is
also empty. **If the KB describes the bowl** — its build, its allergens, "held for a December
launch" — the KB's source dataset had the recipe as `published`, or the build query lost its
`status != "internal"` clause. That is a build-time boundary, fixed by reimporting the seed and
rebuilding the KB, not by anything in the app.

**If the bowl still appears**, the filter didn't save, or `SANITY_CONTEXT_MCP_URL` points at a
different endpoint than the one you edited. **If the vegan count is still 8**, same causes.

The observation to take away: before, the agent's query decided what leaked; after, the server
does. Compare with Mission 2-4, where the engine's checks are advisory and the lake-side
enforcement is still pending.
